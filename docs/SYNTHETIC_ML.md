# Синтетические данные и модель `logreg_v1`

## Зачем нужны эти данные

Это полностью выдуманная учебная среда для проверки ML-пайплайна. Генератор **не** размечает заявки текущим `rules_v1` и **не** использует его `decision`: иначе модель просто повторила бы правила. Метка `default_12m` означает, что в симуляции будущих 12 месяцев бизнесу как минимум в двух месяцах не хватило денег на действующие платежи и платёж по запрошенному кредиту. Это не установленный факт дефолта реального заёмщика.

## Генерация

Код находится в `training/generate_synthetic.py`, файлы — в `data/synthetic_v1/`. `generation.json` фиксирует seed, версию Python, размеры и долю меток. При повторном запуске в той же версии Python с тем же seed CSV воспроизводятся побайтно.

1. Месячная выручка берётся из правосторонне скошенного распределения, ограниченного диапазоном 50 тыс. — 50 млн ₽. Большинство расходов составляют 52–85% выручки; 13% профилей имеют более напряжённые расходы 85–108%.
2. У 18% бизнесов нет текущего долга. В остальных случаях остаток долга задаётся относительно годовой выручки, а ежемесячный платёж вычисляется как аннуитет при условных 20% годовых и сроке 12–60 месяцев. Это связывает долг и платежи между собой.
3. Вероятность просрочек в истории растёт у бизнеса с высокой долей расходов и текущих платежей. Запрашиваемая сумма обычно равна 0,2–1,8 месячной выручки; у 15% заявок она выше, до 3,5 месячной выручки. Срок — 6–60 месяцев.
4. Для каждого бизнеса отдельно разыгрывается годовой шок выручки, затем 12 месячных колебаний выручки и расходов. Исторические просрочки усиливают отрицательный шок, а операционный денежный поток формирует ограниченный резерв. Каждый месяц погашаются текущие платежи и платёж по новому кредиту; после окончания его срока новый платёж прекращается. Если два месяца оказываются неплатёжеспособными, ставится `default_12m=1`.

Симуляция намеренно упрощена: она не описывает налоги, досрочное погашение, реструктуризацию, отрасли и реальные решения банка. Стресс-ставка 20% — параметр расчёта, не предложение клиенту. Независимые выборки `train.csv` (20 000 строк) и `test.csv` (5 000 строк) создаются разными потоками случайных чисел с seed `20261024` и `20261025`. В них только поля публичного запроса, технический `application_id` и целевая метка.

## Обучение и применение

```sh
python -m pip install -r requirements-ml.txt
python -m training.generate_synthetic
python -m training.train_logreg
```

Обучение использует логистическую регрессию со стандартизацией признаков. Признаки вычисляются из семи числовых полей запроса: логарифм выручки, операционная маржа, доля платежей в денежном потоке, отношение долга к годовой выручке, количество просрочек, отношение запроса к годовой выручке и срок. Некоторые отношения ограничиваются сверху для устойчивости на крайних значениях. `application_id`, метка и будущие шоки в модель не входят. Параметры стандартизации обучаются только на `train.csv`.

`training/train_logreg.py` сохраняет коэффициенты, названия и порядок признаков, параметры стандартизации, хеши файлов и метрики в `scoring/artifacts/logreg_v1.json`. Сервис читает этот JSON стандартной библиотекой Python. Прогноз `p` получается логистической функцией; `score = round(100 × (1 − p))`. Шкала согласована лишь с синтетическим миром генератора. Условия `decision`, `approved_amount` и `reasons` вычисляются отдельной политикой из тех же входных показателей и не зависят от выбора модели балла.

Включение модели в PowerShell:

```powershell
$env:SCORING_MODEL = "logreg_v1"
python -m scoring.app
```

В Unix-подобной оболочке: `SCORING_MODEL=logreg_v1 python -m scoring.app`. Для контейнера передайте `-e SCORING_MODEL=logreg_v1`. По умолчанию остаётся `rules_v1`.

## Результат на отдельной тестовой выборке

| Показатель | Значение |
| --- | ---: |
| Доля метки `default_12m=1` | 34,14% |
| ROC AUC | 0,909595 |
| Brier score (меньше лучше) | 0,114287 |
| Brier константного прогноза | 0,224846 |

Для примера из README модель выдаёт 97 баллов и рекомендацию `approved`. При тех же финансовых данных и двух просрочках — 64 балла и `counter_offer` на 1 125 000 ₽. При расходах 2 500 000 ₽ вместо 1 500 000 ₽ — 1 балл и `rejected`.

Высокие метрики здесь показывают, что модель научилась воспроизводить закономерности **нашего симулятора**. Они ничего не говорят о качестве на реальных банковских заявках. Для реального применения нужны исторические исходы, проверка сдвига данных, калибровка и согласованная кредитная политика.
