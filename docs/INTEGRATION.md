# Контракт и интеграция scoring v1

Backend валидирует и сохраняет заявку, проводит проверки ФНС, БКИ и документов. После достаточности данных он вызывает scoring. Scoring возвращает **только балл**. Backend сам применяет правила выбранного продукта, принимает решение, сохраняет статус и объясняет результат клиенту.

```text
frontend -> backend: заявка
backend -> моки ФНС/БКИ и проверка документов
backend -> scoring: POST /v1/score
scoring -> backend: {"score": 0..100}
backend -> frontend: решение, статус, условия и объяснение
```

## Вход

Все поля обязательны; дополнительные запрещены. Денежные суммы — целые рубли. Backend отправляет снимок данных одной заявки. Для одинакового входа `rules_v1` возвращает одинаковый балл.

| Поле | Источник и смысл | Диапазон |
| --- | --- | --- |
| `application_id` | ID сохранённой заявки; метаданные для корреляции, модель его игнорирует | непустая строка до 100 символов |
| `monthly_revenue` | среднемесячная выручка из профиля или анкеты | 0…10¹² ₽ |
| `monthly_expenses` | среднемесячные операционные расходы из анкеты, **без кредитных платежей** | 0…10¹² ₽ |
| `existing_debt` | остаток задолженности из симулятора БКИ | 0…10¹² ₽ |
| `monthly_debt_payments` | действующие ежемесячные кредитные платежи из симулятора БКИ | 0…10¹² ₽ |
| `overdue_count` | количество просрочек из симулятора БКИ | 0…100 |
| `requested_amount` | запрашиваемая сумма из заявки | 1…10¹² ₽ |
| `term_months` | срок из заявки | 1…120 |

Scoring не получает ИНН, ФИО, документы, результаты ФНС, название компании или кредитный продукт. ФНС и документы — предварительные условия вызова и отдельные факторы итогового решения в backend. Данные БКИ поступают в виде трёх числовых признаков. Рекомендация продукта до подачи заявки также находится вне scoring.

## Выход

HTTP 200: `{"score": 100}`. `score` — целое число 0–100; больше означает меньший риск **в рамках учебных правил**. Балл не является вероятностью дефолта, одобрением или суммой кредита. Ветки `approved`, `counter_offer`, `rejected`, `manual_review` принадлежат backend. Scoring не хранит заявку и не изменяет её статус.

Ошибки запроса дают 400, 413, 415 или 422 с `error` и `message`. Ошибка scoring или тайм-аут не должны превращаться в отказ: backend сохраняет заявку в обработке и может повторить вызов.

## Замена модели

Интерфейс `ScoringModel.predict_score(ScoringFeatures) -> int`. Семь числовых признаков собраны в неизменяемом `ScoringFeatures`; `application_id` в модель не попадает. Новую реализацию нужно зарегистрировать в `scoring/models.py:get_model` под новым значением `SCORING_MODEL`. Экземпляр загружается один раз на процесс; его `predict_score` должен быть безопасен при одновременных HTTP-запросах. HTTP и JSON-контракт сохраняются, если сохраняется смысл балла. Новые признаки или иная семантика балла требуют новой версии API.

`rules_v1` использует фиксированные штрафы и условную стресс-ставку 20% годовых для оценки платежа. Это не ставка кредитного предложения. Балл не обучен и не калиброван на исторических данных. Версию модели следует фиксировать в окружении и журнале запуска; backend сможет сохранять её рядом с результатом после согласования такого поля.

## Миграция с прежнего прототипа

Это **несовместимое изменение прежнего `POST /v1/score`** в scoring. Раньше ответ содержал `decision`, `score`, `approved_amount`, `reasons`, `factors`; теперь он содержит ровно `score`. Денежные значения на входе стали строго целыми рублями. Маршрут оставлен как v1, поскольку команда считает прежний прототип черновиком.

Пока backend не обновлён, сквозной сценарий получит `scoring_invalid_response`: текущая интеграция требует старые поля. Разработчику backend нужно:

1. Обновить локальные копии JSON-схем и проверку ответа.
2. После проверок собрать вход по таблице выше.
3. Сохранить балл и применить правила продукта в backend.
4. Не трактовать техническую ошибку scoring как кредитный отказ.

В этом репозитории backend и frontend не изменяются.
