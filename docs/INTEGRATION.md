# Контракт и интеграция scoring v1

Backend валидирует и сохраняет заявку, проводит проверки ФНС, БКИ и документов. После достаточности данных он вызывает scoring. Scoring возвращает балл, факторы и предварительную рекомендацию с причинами. Backend применяет правила продукта, принимает итоговое решение, сохраняет статус и объясняет результат клиенту.

```text
frontend -> backend: заявка
backend -> моки ФНС/БКИ и проверка документов
backend -> scoring: POST /v1/score
scoring -> backend: decision, score, approved_amount, reasons, factors
backend -> frontend: решение, статус, условия и объяснение
```

## Вход

Все поля обязательны; дополнительные запрещены. Денежные суммы — целые рубли. Backend отправляет снимок данных одной заявки. Для одинакового входа обе доступные версии модели возвращают одинаковый балл.

| Поле | Источник и смысл | Диапазон |
| --- | --- | --- |
| `application_id` | ID сохранённой заявки; метаданные для корреляции, модель его игнорирует | непустая строка до 100 символов |
| `monthly_revenue` | среднемесячная выручка из профиля или анкеты | 0…10¹² ₽ |
| `monthly_expenses` | среднемесячные операционные расходы из анкеты, **без кредитных платежей** | 0…10¹² ₽ |
| `existing_debt` | остаток задолженности из симулятора БКИ | 0…10¹² ₽ |
| `monthly_debt_payments` | действующие ежемесячные кредитные платежи из симулятора БКИ | 0…10¹² ₽ |
| `overdue_count` | количество просрочек из симулятора БКИ | 0…100 |
| `requested_amount` | запрашиваемая сумма из заявки | 1…10¹² ₽ |
| `term_months` | срок из заявки | 1…120 |

Scoring не получает ИНН, ФИО, документы, результаты ФНС, название компании или кредитный продукт. ФНС и документы — предварительные условия вызова и отдельные факторы итогового решения в backend. Данные БКИ поступают в виде трёх числовых признаков. Рекомендация продукта до подачи заявки также находится вне scoring.

## Выход

HTTP 200 содержит ровно пять полей: `decision`, `score`, `approved_amount`, `reasons`, `factors`. `score` — целое число 0–100; больше означает меньший риск по выбранной демонстрационной модели. Он не является подтверждённой вероятностью дефолта реального клиента. `decision` принимает `approved`, `counter_offer`, `rejected` и является предварительной рекомендацией. `approved_amount` равен запрошенной сумме при `approved`, меньше неё при `counter_offer`, нулю при `rejected`. Это рекомендуемая, а не выданная сумма. `reasons` — непустой список причин. Scoring не хранит заявку и не изменяет её статус.

`factors` содержит ровно шесть показателей: `operating_cash_flow` = выручка − операционные расходы (₽/месяц); `operating_margin` = поток / выручка; `estimated_new_monthly_payment` = оценочный платёж по **запрошенной** сумме при 20% годовых; `debt_service_share` = (текущие платежи + оценочный платёж) / поток; `existing_debt_to_annual_revenue` = остаток долга / (12 × месячная выручка); `overdue_count` = входное количество просрочек. Два отношения равны `null`, когда их знаменатель не положителен. Отношения округлены до четырёх знаков, платёж — до копеек; правила применяются к неокруглённым числам.

## Правила v1

1. По умолчанию `logreg_v1` считает балл как `round(100 × (1 − p))`, где `p` — прогноз синтетической просрочки. При `SCORING_MODEL=rules_v1` балл начинается со 100: вычитаются штрафы за просрочки, маржу, долю платежей и отношение долга к годовой выручке. Подробности в [SYNTHETIC_ML.md](SYNTHETIC_ML.md).
2. Рекомендация `rejected` выдаётся при трёх и более просрочках, неположительном денежном потоке, марже ниже 10% или долге не менее 150% годовой выручки. Каждая причина перечисляется отдельно.
3. Рекомендация `approved` на полную запрошенную сумму требует отсутствия просрочек, маржи не менее 15%, долга меньше годовой выручки и доли всех платежей не более 45% потока.
4. Иначе рассчитывается меньшая сумма: суммарные платежи не выше 55% потока, верхний лимит — 75% запроса при просрочках либо 85% без них. Если получается не менее 20% запроса, возвращается `counter_offer`; иначе `rejected`. Все суммы — целые рубли.

Балл и рекомендация используют одни и те же входные показатели, но рекомендация имеет жёсткие пороги. Поэтому высокий балл сам по себе не гарантирует `approved`. При будущей замене модели пороги рекомендаций нужно перепроверить. Итоговый статус и условия кредита определяет backend.

Ошибки запроса дают 400, 413, 415 или 422 с `error` и `message`. Ошибка scoring или тайм-аут не должны превращаться в отказ: backend сохраняет заявку в обработке и может повторить вызов.

## Замена модели

Интерфейс `ScoringModel.predict_score(ScoringFeatures) -> int`. Семь числовых признаков собраны в неизменяемом `ScoringFeatures`; `application_id` в модель не попадает. Новую реализацию нужно зарегистрировать в `scoring/models.py:get_model` под новым значением `SCORING_MODEL`. Экземпляр загружается один раз на процесс; его `predict_score` должен быть безопасен при одновременных HTTP-запросах. HTTP и JSON-контракт сохраняются, если сохраняется смысл балла. Новые признаки или иная семантика балла требуют новой версии API.

`rules_v1` использует фиксированные штрафы; `logreg_v1` загружает проверяемые коэффициенты из JSON-артефакта и работает без внешних библиотек в HTTP-сервисе. Обе версии используют условную стресс-ставку 20% годовых для оценки платежа. Это не ставка кредитного предложения. `logreg_v1` обучен лишь на синтетических данных. Версию модели следует фиксировать в окружении и журнале запуска; backend сможет сохранять её рядом с результатом после согласования такого поля.

## Согласование с backend

Форма ответа соответствует строгому декодеру в текущем Go backend: названия пяти полей и шести факторов, enum и nullable-показатели совпадают. Backend сохраняет ответ как результат скоринга, затем отдельно применяет проверки ФНС, документов и правила продукта в Decision Engine. Техническая ошибка scoring или тайм-аут не являются кредитным отказом; backend сохраняет техническое состояние и ограниченно повторяет вызов. Общий Docker Compose репозитория `smart-credit` уже связывает frontend, backend, scoring и PostgreSQL.

По сравнению с первоначальным прототипом ответ снова содержит рекомендацию и факторы. Вход v1 остаётся строгим: денежные значения принимаются только целыми рублями. В этом репозитории backend и frontend не изменяются.
